# tfmtp — техническое описание

Документ для тех, кто хочет понять, почему встроенный MTP TreeFrogUI не работал, как устроено исправление, как его собрать и как повторить диагностику на другой консоли. Инструкция по установке — в [README.ru.md](../README.ru.md). [English version](TECHNICAL.md).

---

## 1. Система

| Компонент | Значение |
|---|---|
| SoC | HiChip HC16xx, MIPS32 little-endian, ~43 МБ ОЗУ доступно Linux (`MemTotal: 43160 kB`), своп 128 МБ в `cubegm/pagefile.sys` |
| Ядро | `Linux 4.4.186-release #23 PREEMPT ... mips` |
| Прошивка | TreeFrogUI v1.8.0_u поверх стоковой CubeGM, профиль `GB350` |
| USB | два контроллера MUSB OTG: `usb@18844000` → `musb-hdrc.0.auto` (разъём к ПК), `usb@18850000` → `musb-hdrc.1.auto`; при загрузке оба в host-режиме (`b_idle`) |
| Переключение роли | `/sys/devices/platform/soc/18844000.usb/musb-hdrc.0.auto/mode` ← `peripheral` (читается как `b_peripheral`) |
| Gadget | configfs + `libcomposite`; MTP-функция `usb_f_mtp.ko` (Android-драйвер `f_mtp`) из `cubegm/modules/4.4.186-release/` |
| Узел MTP | `/dev/mtp_usb`, misc `10, 58`; создаётся при `mkdir functions/mtp.usb0` |
| Карта | microSD 16 ГБ, FAT32 (`vfat`, `iocharset=utf8`), смонтирована в `/mnt/sdcard`; ~34 000 объектов |

Цепочка штатного TreeFrogUI: пункт меню USB → `cubegm/usb_mtp.sh` → `cubegm/usb_mode.sh mtp` → функция `run_mtp_mode()`:

1. создаёт gadget в configfs: VID/PID `18D1:4E22`, Microsoft OS descriptors, `compatible_id=MTP`;
2. включает роль `peripheral` и привязывает UDC;
3. запускает `cubegm/mtp-server /mnt/sdcard` и `cubegm/usb_exit_watcher <pid>`. Наблюдатель читает кнопки из общей памяти `cubevol` (`ftok("/tmp/joy_key",'a')`, 4 байта, B = бит 14 `0x4000`) и по нажатию B убивает сервер.

## 2. Как была найдена причина

### 2.1. Симптом

- Windows видит «USB-устройство MTP» (`USB\VID_18D1&PID_4E22`), драйвер `wpdmtp.inf` / служба `WUDFWpdMtp` ставится без ошибок.
- В Проводнике консоль не появляется.
- В журнале `Microsoft-Windows-WPD-MTPClassDriver/Operational`:
  - событие 1007 — «Устройство не отвечает на операцию **0x1002** … попытка отмены операции; HRESULT 0x802A0006»;
  - событие 1006 — «Сбой запуска драйвера, HRESULT 0x802A0006».

### 2.2. Инструменты

- **Сторона ПК:** USBPcap + tshark — сырые USB-пакеты; журналы `WPD-MTPClassDriver` (Operational и Analytic), `DriverFrameworks-UserMode`, `Kernel-PnP`; монитор подключений. Это скрипты из `tools/`.
- **Сторона консоли:** в `usb_mode.sh` добавлена трассировка, которая включается файлом `log.txt` в корне карты. Каждые 2 с она пишет для процесса сервера:
  - по каждому потоку — состояние, `wchan` (где поток ждёт в ядре), текущий системный вызов, потраченное время CPU;
  - открытые файлы (видно, какую папку он сейчас читает), RSS, свободную память и своп;
  - состояние UDC и новые строки `dmesg`.

### 2.3. Хронология (одна и та же сессия с двух сторон)

| ПК (USBPcap + журнал драйвера) | Консоль (`log.txt`) |
|---|---|
| 22:44:32.194 — bulk OUT 16 байт: **OpenSession** (`0x1002`, tid 0, SessionID 1); передача завершена успешно | `mtp-server` в состоянии `R`, 100 % CPU, `wchan=0`, открыты `/mnt/sdcard/MAME`, затем `roms/*`, `cubegm/cheat/*`… — **обход всей карты** |
| 22:45:02.300 — через 30 с: `GetDeviceStatus` (class request 0x67), отмена ожидающего bulk IN (`USBD_STATUS_CANCELED 0xC0010000`), «сбой запуска драйвера» | обход продолжается |
| 22:47:14 — переподключение кабеля → новый OpenSession, через 30 с снова отмена | обход продолжается |
| — (Windows больше ничего не шлёт) | через **167 с** после старта: `MTP indexed 34036 objects under /mnt/sdcard`, затем `MTP_REQ op=1002` → `MTP_RESP op=1002 code=2001` (OK) — ответ уходит в пустоту |
| — | далее 5 минут `S`, `wchan=mtp_read`: сервер исправно ждёт команд, которых больше нет |

**Вывод:**

- USB-железо, драйвер `f_mtp` и протокол исправны: сервер в итоге ответил корректно.
- Штатный `mtp-server` (закрытый, на основе старого Android `MtpServer`) **сначала индексирует всю карту**, примерно 200 объектов/с на этом CPU, и только потом читает первую команду.
- Windows ждёт OpenSession ~30 с и не повторяет попытку до переподключения кабеля.

Память ни при чём: RSS сервера ~8 МБ, своп свободен.

### 2.4. Попутная ловушка: «Неизвестное USB-устройство»

Первая попытка исправить порядок, «подключать USB только после индексации», вызвала у Windows «сбой запроса дескриптора устройства» (`USB\VID_0000&PID_0002`). Причина: роль `peripheral` включалась до привязки gadget. MUSB уже подтягивает D+, ПК начинает нумерацию, а отвечать на дескрипторы некому. Поэтому роль нужно переключать **непосредственно перед** записью в `UDC`, а до этого контроллер держать в host-режиме: ПК не видит ничего.

## 3. Решение

### 3.1. tfmtp — MTP-сервер с ленивым перечислением

Один файл на C (`src/tfmtp.c`, ~1000 строк), без зависимостей, статически собранный под MIPS. Запуск совместим со штатным: `tfmtp <корень>`.

**Ленивые хэндлы.**

- MTP-хэндл объекта выдаётся только тогда, когда ПК перечисляет папку, в которой он лежит (`GetObjectHandles` / `GetObjectPropList` с depth=1).
- Таблица объектов: `{родитель, имя, папка?, удалён?}`, хэш-таблица по (родитель, имя), поэтому повторное перечисление выдаёт те же хэндлы.
- Полный путь собирается подъёмом по родителям.
- Размер и даты берутся `stat()` в момент запроса.

**Транспорт — штатный интерфейс Android `f_mtp`:**

- команды и короткие данные — `read()`/`write()` на `/dev/mtp_usb`, буфер 16 384 байта (лимит `mtp_rx_req_len` драйвера);
- отдача файла ПК — `ioctl(MTP_SEND_FILE_WITH_HEADER = 0x80204D04, struct mtp_file_range)`. Заголовок контейнера и ZLP формирует ядро. Номер ioctl и размер структуры (32 байта) сверены с машинным кодом штатного `mtp-server`: там `lui 0x8020` + `addiu 0x4D01/0x4D03/0x4D04`;
- приём файла с ПК — циклом `read()` по 16 КБ с записью в файл. Данные из ПК вычитываются **всегда** до конца фазы данных, даже при ошибке записи, иначе протокол рассинхронизируется. Ускорение через `MTP_RECEIVE_FILE (0x80204D01)` — возможное улучшение.

**Поддерживаемые операции** (объявляются в `GetDeviceInfo`):

| Группа | Операции |
|---|---|
| Сессия и устройство | `GetDeviceInfo`, `OpenSession`, `CloseSession`, `GetDevicePropDesc`/`GetDevicePropValue` (только `0xD402` DeviceFriendlyName = «R36S») |
| Хранилище | `GetStorageIDs` (одно, `0x00010001`), `GetStorageInfo` (`statvfs`, тип RemovableRAM, иерархическая ФС) |
| Перечисление | `GetNumObjects`, `GetObjectHandles`, `GetObjectInfo`, `GetObjectReferences` (всегда пусто) |
| Чтение | `GetObject`, `GetPartialObject` |
| Запись | `SendObjectInfo` (для формата `0x3001` сразу `mkdir`), `SendObject`, `DeleteObject` (рекурсивно), `SetObjectPropValue` (переименование через `0xDC07`/`0xDC44`) |
| Свойства | `GetObjectPropsSupported`, `GetObjectPropDesc`, `GetObjectPropValue`, `GetObjectPropList` (depth 0 и 1; группы и depth>1 — коды `0xA805`/`0xA808`) |

- **Свойства объектов:** StorageID, ObjectFormat, ProtectionStatus, ObjectSize (u64), ObjectFileName (можно менять), DateCreated, DateModified, ParentObject, PersistentUID, Name.
- **Форматы:** Undefined, Association (папка), текст, WAV, MP3, AVI, JPEG, BMP, GIF, PNG, MP4. Определяются по расширению, всё прочее — Undefined.
- **Строки:** UTF-8 (FAT смонтирован с utf8) ↔ UTF-16LE MTP-строк, включая суррогатные пары.
- **Расширение производителя:** `microsoft.com: 1.0;` (VendorExtensionID 6).

**Журнал:** каждая операция пишется в stderr (`TFMTP <uptime> REQ/RESP ...`, время обработки, скорость передач). `usb_mode.sh` направляет stderr в `/mnt/sdcard/log.txt` только если этот файл существует, иначе в `/dev/null`. Метки времени — `CLOCK_MONOTONIC` (совпадают с uptime и `dmesg`).

### 3.2. Изменения в `usb_mode.sh`

Полный diff — `patch/usb_mode.sh.patch` (5 блоков, проверен `git apply` и `patch -p1` на оригинале v1.8.0_u).

1. **Выбор сервера:** `cubegm/tfmtp`, если он есть и исполняемый, иначе штатный `mtp-server`. Переменная `TF_USB_MTP_RESPONDER` по-прежнему имеет приоритет.
2. **Порядок запуска:** gadget создаётся в host-режиме → запускается сервер и наблюдатель кнопки B → скрипт ждёт, пока `/proc/<pid>/wchan` сервера станет `mtp_read` (сервер готов). На экран раз в 10 с выводится «Preparing MTP: scanning SD card files… N s (B = cancel)», предел ожидания 900 с (`TF_USB_MTP_INDEX_TIMEOUT`). Только потом включается роль `peripheral` и привязывается UDC. Если сервер завершился во время ожидания (нажата B), USB вообще не включается. Для `tfmtp` ожидание занимает 0 с.
3. **Трассировка** `mtp_trace_init/tick/kmsg`: только при наличии `log.txt`; без него функции сразу возвращаются.

## 4. Сборка tfmtp

Нужен [Zig](https://ziglang.org/) — он содержит clang и musl для MIPS. Проверено на Zig 0.17.0 под Windows.

```sh
# консоль (статический MIPS32 LE, soft-float — без зависимостей от библиотек карты)
zig cc -target mipsel-linux-musleabi -mcpu=mips32 -static -Os -s -o tfmtp src/tfmtp.c

# самопроверка на ПК (Windows): тот же код протокола с имитацией USB и тестовой папкой
zig cc -DTFMTP_TEST -Dstrcasecmp=_stricmp -o tfmtp_test.exe src/tfmtp.c
tfmtp_test.exe            # → "SELF-TEST: all checks passed"
```

Самопроверка прогоняет сценарий из 21 проверки:

- `GetDeviceInfo` → `OpenSession` → хранилище;
- список корня и `GetObjectInfo`;
- `GetObjectPropList` depth=1;
- чтение файла 40 000 байт и частичное чтение;
- создание папки, загрузка 70 000 байт кусками по 16 КБ с русским именем, обратное чтение и побайтное сравнение;
- переименование, удаление папки, недействительность хэндла после удаления, неизвестная операция.

Сборка `-target mipsel-linux-musl` без `eabi` в Zig 0.17 не работает («unable to provide libc»): нужен суффикс `musleabi` или `musleabihf`. Выбран `musleabi` (soft-float): точный FPU ядра SoC неизвестен, а плавающая точка в tfmtp нужна только для журнала.

## 5. Результаты на консоли

Сессия после установки (Windows 10, кабель напрямую):

| Метрика | Штатный `mtp-server` | `tfmtp` |
|---|---|---|
| Готов отвечать после запуска | 167 с (индексация 34 036 объектов) | 0 с |
| Windows открыла сессию | никогда (таймаут 30 с) | через ~0,5 с после привязки USB |
| Ошибки в первой сессии | — | 0 из 930 запросов |
| Память сервера (RSS) | ~8,3 МБ | ~0,3 МБ |
| Корень (34) / `roms` (109) / `roms\FC` (2 908) | — | мгновенно / ~1,3 с / ~52 с |
| 24 МБ на консоль | — | 7,3 с на стороне консоли (**3,3 МБ/с**) |
| 24 МБ на ПК | — | 2,4 с на стороне консоли (**9,8 МБ/с**), SHA-256 совпал |

**Почему большие папки медленные** (разбор журнала `roms\FC`, 17 456 запросов за 59 с):

- Windows на каждый объект делает `GetObjectPropList` для `0xDC02`, `0xDC03`, `0xDC04`, затем `GetObjectInfo`, `GetObjectPropList(все)`, `GetObjectReferences` — 6 запросов на объект; depth=1 для пакетного получения она не использует;
- серверное время — 41 с из 59, почти всё в первом `stat()` каждого файла (`GetObjectPropList` в среднем 2,9 мс, `GetObjectInfo` после этого — 0,09 мс);
- `vfat_lookup` → `fat_search_long` ищет имя, просматривая каталог с начала, поэтому стоимость O(позиция), а суммарно O(n²) на папку;
- кэшировать результат бессмысленно: дорогой только первый `stat`, повторные попадают в dcache;
- возможный путь ускорения — разбирать каталог FAT напрямую с блочного устройства, но для этой версии это сочтено неоправданным.

## 6. Как повторить диагностику на другой консоли или прошивке

1. **Проверить предпосылки на консоли**, через `log.txt` при запуске USB-режима или любым доступным shell:
   - есть `/dev/mtp_usb` после создания функции `mtp.usb0` (строка `TRACE devnode:` в журнале);
   - имя UDC (`ls /sys/class/udc`) совпадает с `UDC_NAME` в `usb_mode.sh` (здесь `musb-hdrc.0.auto`);
   - архитектура: `uname -m` = `mips`, little-endian. `tfmtp` собран под MIPS32 LE. Для другой архитектуры пересоберите с подходящим `-target`, код переносимый.
2. **Проверить ioctl драйвера** (если ядро другое): найти в штатном `mtp-server` константы `0x8020`/`0x4D04`, как в разделе 3.1, либо просто убедиться по журналу `tfmtp`, что `GetObject` передаёт файл (`sent N bytes`), а не пишет `send file failed`.
3. **Снять картину с двух сторон:**
   - на консоли — `log.txt` в корне карты;
   - на ПК — `tools/usb_trace_setup.ps1` (один раз, от администратора, затем перезагрузка), `tools/usb_capture.ps1` во время теста, после — `tools/usb_mtp_report.ps1`.

   Сопоставлять по времени: строки `TFMTP <uptime>` и `KMSG [uptime]` на консоли, время ПК в отчёте. Привязка — событие подключения (`gadget connet` в `dmesg` ↔ появление устройства в мониторе).
4. **Признаки:**
   - запрос ушёл (bulk OUT успешно), а ответа нет, и сервер в это время `R` со 100 % CPU — сервер занят (индексация);
   - сервер в `wchan=mtp_read`, а запрос ушёл — проблема ниже, в драйвере или кабеле;
   - ПК вообще не посылает запросов, а в `KMSG` нет `gadget connet` — USB не поднялся (роль, UDC, кабель).
