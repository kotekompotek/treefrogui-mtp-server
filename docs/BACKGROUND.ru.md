# Фоновый MTP, удалённое управление и запись: как это сделано

Этот документ описывает вторую часть проекта (v2.0): MTP включается сам при подключении к ПК и работает в фоне, пока идут меню и игры. Порт OTG при этом продолжает работать с мышками и флешками, а консолью можно управлять с ПК через то же MTP-соединение. Первая часть (почему штатный MTP не работал и как устроен `tfmtp`) описана в [TECHNICAL.ru.md](TECHNICAL.ru.md).

Всё ниже проверено на одной консоли: клон R36S на HiChip HC16xx, TreeFrogUI v1.8.0_u (профиль GB350), Windows 10 22H2. Цифры взяты из журналов этой консоли.

---

## 1. Задача и ограничения

Чего хотели:

1. MTP запускается сам, как только консоль подключена к ПК, без пункта меню USB (MTP).
2. В это время меню и игры работают как обычно, MTP идёт в фоне.
3. Порт OTG не сидит постоянно в режиме устройства: мышка, геймпад или флешка через OTG-переходник должны продолжать работать.
4. С ПК можно управлять консолью полностью: команды Linux, файлы, кнопки, снимки экрана, перезагрузка. После перезагрузки связь поднимается сама.
5. По возможности MTP на обоих USB-портах.

Что выяснилось сразу, из дампов ядра (`/proc/kallsyms`, конфиг сборки модулей TreeFrog):

- **В ядре нет TCP/IP** (нет `tcp_v4_rcv`, `inet_init`). Значит, сеть по USB (RNDIS/ECM), ssh и adb невозможны без пересборки ядра. Канал управления придётся делать поверх самого MTP.
- **Нет `uinput` и нет `/dev/input`**. Кнопки читаются не через evdev: стоковый демон `cubevol` опрашивает GPIO и кладёт состояние в разделяемую память SysV `ftok("/tmp/joy_key",'a')`, а меню и эмуляторы читают её оттуда.
- Ядро позволяет загружать модули обычным `insmod`: TreeFrog так и загружает `usb_f_mtp.ko`.

## 2. Канал управления: собственные MTP-команды

В MTP есть диапазон кодов операций для расширений производителя. Windows умеет отправлять устройству произвольные MTP-команды через WPD (Windows Portable Devices): у драйвера MTP есть категория «MTP extension» (`WPD_COMMAND_MTP_EXT_EXECUTE_COMMAND_WITH_DATA_TO_READ` и `..._TO_WRITE`, `READ_DATA`/`WRITE_DATA`, `END_DATA_TRANSFER`). Значит, не нужен ни отдельный драйвер, ни libusb: работает стандартный драйвер Windows, и Проводник может быть открыт одновременно.

**Проверка до правок консоли.** Через WPD (Python + `comtypes`, обёртки сгенерированы из `PortableDeviceApi.dll`) отправили старому `tfmtp` обычную `GetDevicePropValue(0xD402)` и получили «R36S». Механизм работает.

**`tfmtp` 1.1/1.2: операции 0x9A00–0x9A04.**

| Код | Операция | Данные | Ответ |
|---|---|---|---|
| 0x9A00 | TF_Info | → ПК: строка версии | — |
| 0x9A01 | TF_Exec(flags) | ПК →: команда для `/bin/sh -c` | id задачи |
| 0x9A02 | TF_Read(job, max, wait_ms) | → ПК: stdout+stderr | состояние, код выхода, остаток в буфере |
| 0x9A03 | TF_Write(job, flags) | ПК →: данные для stdin | сколько принято |
| 0x9A04 | TF_Signal(job, sig) | — | sig 0 = забыть задачу |

Устройство:
- задача запускается через `fork` + `setsid` + `/bin/sh -c`; stdout и stderr идут в общий неблокирующий канал;
- вывод копится в буфере 512 КБ на задачу (до 8 задач). Когда буфер полон, `tfmtp` перестаёт читать канал, и процесс просто ждёт. Память не растёт, а потоковые программы (например, запись) получают естественный «тормоз»;
- `TF_Read` ждёт данные не дольше 2 с, поэтому MTP-сеанс Проводника не подвисает;
- операции включены, только если на карте есть файл `cubegm/tfmtp.remote`. Без него консоль ведёт себя как в v1.0 и даже не объявляет эти коды в `DeviceInfo`;
- у дочерних процессов сбрасывается игнорирование SIGPIPE (иначе `cat | head` ведёт себя странно), закрываются все лишние дескрипторы, в том числе `/dev/mtp_usb`.

**Загрузка новой версии без кардридера.** Работающий файл в Linux можно удалить: процесс продолжает работать с удалённым inode. Поэтому через MTP удалили `cubegm/tfmtp`, записали новый, проверили SHA-256 и один раз перезашли в USB-режим.

ПК-клиент: [`pc/r36.py`](../pc/r36.py). Первая же команда `id; uname -a` вернула `uid=0(root)`.

Подводный камень: в `sh -c 'cat > f && ... &'` фоновый список получает stdin из `/dev/null`, и `cat` ничего не читает. Фоновым надо делать только последнюю команду.

## 3. Какой порт может работать как USB-устройство

На SoC два контроллера MUSB: `musb-hdrc.0.auto` (0x18844000) и `musb-hdrc.1.auto` (0x18850000). В device tree у обоих `dr_mode = "host"`, линий ID и VBUS-детекта нет.

**Порт DC.** Опыт (скрипт с журналом каждые 0,25 с): кабель от ПК переставляли из OTG в DC, второй контроллер переводили в режим устройства и привязывали к нему MTP-гаджет.

```
 19.83 adc5=104 ...                 <- зарядка через DC видна
 22.34 PHASE4 musb1 -> peripheral, bind gadget to musb-hdrc.1.auto
 ... 30 с: u1=not_attached, сброса шины от ПК нет
 52.27 RESULT DC_NO_DATA
```

ПК ни разу не сбросил шину. **Порт DC только заряжает, линий данных там нет.** MTP на нём невозможен на уровне платы.

**Порт OTG** (musb0) — единственный с данными. Значит, один и тот же разъём должен быть и хостом (для мышки или флешки), и устройством (для ПК). TreeFrog тоже использует musb0 и для `usb_host.sh` (флешка), и для MTP.

## 4. Как понять, что подключён ПК

Обычные признаки на этой плате не работают:

| Признак | Что показал опыт |
|---|---|
| VBUS (`DEVCTL` бит VBUS, sysfs `vbus`) | всегда «есть»: консоль сама подаёт 5 В на OTG-порт |
| состояние UDC | после выдёргивания кабеля остаётся `configured` (проверено 300 с) |
| `/dev/check_adc5` (датчик зарядки) | видит только зарядку через DC; ПК в порту OTG даёт 0, хотя батарея при этом заряжается |
| `POWER`/suspend | бит не меняется |

**Рабочий признак — регистр FRAME (смещение 0x0C) контроллера MUSB.** Это номер кадра, который хост рассылает пакетами SOF каждую миллисекунду. Пока ПК на связи, счётчик растёт, без ПК стоит:

```
frame0=0x0259  frame0=0x02CD  frame0=0x0312  ...   (ПК подключён, интервалы 3 мс)
musb0=idle                                         (кабель вынут)
```

Чтение: два раза с паузой 3 мс через `mmap` `/dev/mem` (в отладке — `devmem 0x1884400C 16`).

## 5. Служба tfusbd: переключение хост/устройство

Свежепривязанный гаджет стартует в состоянии `not attached`, и любое другое состояние сразу после привязки означает, что хост нас сбросил. Получается автомат:

```
IDLE:  2 с HOST        — появилось устройство в /sys/bus/usb/devices/1-* ?  → DEV
       2 с PERIPHERAL  — FRAME растёт или UDC ушёл из "not attached" ?     → PC
PC:    раз в секунду проверяем FRAME; 3 промаха подряд → ПК ушёл → IDLE
DEV:   ждём, пока устройство пропадёт → IDLE
```

Журнал службы на консоли:

```
 57.74 PC gone (udc=configured)
 61.60 USB device attached: COMPANY  USB Device  (idVendor=09da class=03)   <- мышка
 65.05 USB device removed
 73.96 PC detected (udc=configured)
```

- `tfmtp` работает всё время. Пока гаджет отвязан, его чтение просто возвращает ошибку, и он ждёт.
- Перед режимом устройства гаджет всегда привязывается заново. Режим устройства без привязанного гаджета даёт в Windows «Unknown USB device (device descriptor request failed)» (см. TECHNICAL).
- Первая версия была на shell и вызывала `devmem` по нескольку раз в секунду. Версия на C ([`src/tfusbd.c`](../src/tfusbd.c)) читает регистр через `mmap` и в простое тратит 0% процессора (замер за 10 с во время игры GBA).

## 6. Как не мешать играм

`tfmtp` запускается с политикой планировщика **`SCHED_IDLE`**: он получает процессор только тогда, когда он не нужен игре. В musl нет `sched_setscheduler` (функция намеренно возвращает ошибку), поэтому вызов сделан напрямую через `syscall(SYS_sched_setscheduler, ...)`. Удалённые задачи (кнопки и прочее) `tfmtp` наоборот возвращает в обычный класс, иначе нажатия запаздывали бы в нагруженной игре.

Замер: 24 МБ туда и обратно во время игры.

| | Contra (NES), обычный приоритет | Ace Air Combat (GBA), `SCHED_IDLE` |
|---|---|---|
| ПК → консоль | 2,1 МБ/с | 1,7 МБ/с |
| консоль → ПК | 7,3 МБ/с | 7,6 МБ/с |
| рывки картинки | один за передачу | не замечено |
| SHA-256 | совпадает | совпадает |

**Утечка памяти в picoarch (v2.1.1).** picoarch распаковывает zip-игры в `/tmp/pa-<имя>`, а `/tmp` — это оперативная память. Файлы остаются до перезагрузки. На консоли с 43 МБ после игры в GBA на 8 МБ эмулятор PS1 (pcsx4all) убивался ядром из-за нехватки памяти через три секунды после запуска (`Out of memory: Kill process … (pcsx4all)` в `dmesg`). Теперь раз в 10 секунд, пока игра не запущена (в picoarch только меню FrogUI или ничего), tfusbd удаляет файлы `/tmp/pa-*`, которые никто не держит открытыми (`/proc/*/fd`) и не отображает в память (`/proc/*/maps`): `housekeeping: freed 1024 KB of RAM: /tmp/pa-test game.gba`.

## 7. Перехват сеанса из меню и чёрный экран

Если служба стартует, когда уже открыт пункт меню USB (MTP), она забирает сеанс себе. Первая версия убивала `usb_mode.sh` сигналом SIGKILL, чтобы не сработала его уборка. Итог: меню запускалось и рисовало кадры в память (снимок `fb0` показывал меню), **но экран оставался чёрным даже после перезапуска меню**, до перезагрузки. Гипотезу «экран гасит стоковый `cubevol`, пока подключён USB» проверили: отключили USB на минуту — экран остался чёрным, гипотеза не подтвердилась.

Решение: завершать сеанс так же, как кнопка B. Служба создаёт `/tmp/treefrog_mtp_exit`, отправляет `SIGTERM` ответчику и ждёт, пока `usb_mode.sh` сам уберёт гаджет. Меню возвращается нормально.

Пункт меню USB (MTP) при работающей службе больше не нужен. Пропатченный `usb_mtp.sh` в этом случае сразу возвращает в меню.

## 8. Автозапуск и перезагрузка

TreeFrog при загрузке запускает `cubegm/zhijack.sh`: он генерируется под устройство, поэтому в него вставляются 2 строки (см. [`patch/zhijack.hook`](../patch/zhijack.hook)) перед циклом меню, после запуска `cubevol`:

```sh
[ -f /mnt/sdcard/cubegm/tfusbd.on ] && [ -x /mnt/sdcard/cubegm/tfusbd.sh ] && \
    /mnt/sdcard/cubegm/tfusbd.sh start >/dev/null 2>&1
```

`tfusbd.sh start` копирует бинарник в `/tmp` и запускает его оттуда, поэтому карта не остаётся занятой. Включение и выключение — файл `cubegm/tfusbd.on`.

Перезагрузка с ПК: `python r36.py reboot` выполняет `sync; reboot`. Через 27 с консоль снова на связи: служба стартовала на 9-й секунде загрузки, ПК найден на 17-й.

## 9. Кнопки

Состояние кнопок — 32-битное слово в разделяемой памяти, биты по `frogui/keymap.txt`: UP=4, DOWN=6, LEFT=7, RIGHT=5, A=13, B=14, X=12, Y=15, L1=10, R1=11, START=3, SELECT=0.

Опыт `tfkey probe`: ставим неиспользуемый бит 31 и засекаем, когда `cubevol` его затрёт.

```
marker cleared in 20/20 tries: min 4.97 ms avg 19.53 ms max 47.22 ms
```

`cubevol` перезаписывает слово каждые ~20–50 мс. Поэтому [`tfkey`](../src/tfkey.c) держит нажатие, подтверждая биты каждые 0,2 мс, а между нажатиями в последовательности делает паузу 60 мс, чтобы игра увидела отпускание. Проверка: `r36.py key press START` поставил Contra на паузу, повторное нажатие снял, лишних срабатываний не было.

## 10. Снимки экрана

`fb0` — RGB565, 640×(480×23 страниц). Видимая страница указана в `/sys/class/graphics/fb0/pan`. `fb1` — ARGB-оверлей `cubevol` (батарея, громкость). [`pc/fbshot.py`](../pc/fbshot.py) читает видимую страницу `fb0` и `fb1` через `dd`, накладывает их по альфе и сохраняет PNG без сторонних библиотек. Работает и в меню, и в играх (проверено на NES и GBA). В режиме USB (MTP) из меню видимая страница содержит мусор: меню там уже закрыто.

## 11. Безопасность

`cubegm/tfmtp.remote` даёт **root-доступ любому ПК**, к которому подключена консоль. Поэтому удалённое управление по умолчанию выключено и включается только `install_remote.bat` (ключ `-Remote`). Если оно не нужно, удалите этот файл.

## 12. Запись видео и звука (v2.1)

**Где брать кадры и звук.** Игры выводят картинку и звук не сами: picoarch загружает библиотеку драйвера (`driver_gb350.so` на GB350) и вызывает из неё `video_driver_disp_frame` и `sound_driver_playframe`. Если подставить вместо драйвера свою библиотеку-прослойку, она увидит каждый кадр и каждый кусок звука ровно в момент вывода, в родном разрешении игры, без чтения экрана и без лишнего копирования.

Что выяснили по исходникам picoarch (TreeFrogUI_picoarch, `plat_sdl.c`, `hwdisp.c`):
- путь к драйверу picoarch **не берёт** из `TF_DRIVER` в `/tmp/tfdevice.env`: он зашит для каждого `TF_DEVICE`, а переопределяется переменной окружения `PICOARCH_DRIVER`. `TF_DRIVER` читают только просмотрщики картинок и видео;
- `int video_driver_disp_frame(void *src, int w, int h, int pitch_bytes)` — кадр RGB565;
- `int sound_driver_init(void *dev, int rate, int channels)` вызывается с `(NULL, 48000, 2)`;
- `int sound_driver_playframe(const void *buf, int n)` — `n` это число стереокадров s16 (обычно 480 = 10 мс). Отрицательный результат заставляет picoarch переинициализировать звук;
- кроме функций, picoarch берёт через `dlsym` и переменную `g_render` из драйвера.

**Прослойка `tfshim_gb350.so`** ([`capture/tfshim.c`](../capture/tfshim.c)):
- экспортирует ровно тот же набор символов, что настоящий драйвер: 117 функций и 7 переменных. Список берётся из `.dynsym` драйвера скриптом [`capture/gen_tramp.py`](../capture/gen_tramp.py), читаются только имена;
- 114 функций — «трамплины» из 8 инструкций MIPS: прыжок в настоящую функцию с нетронутыми регистрами аргументов, стеком и адресом возврата;
- перехвачены только `video_driver_disp_frame`, `sound_driver_playframe` и `sound_driver_init` (для частоты и числа каналов);
- переменные драйвера прослойка при загрузке перенаправляет в своей таблице символов на настоящие, так что `dlsym(…, "g_render")` возвращает адрес из настоящего драйвера;
- пока запись не идёт, перехват стоит 18 инструкций на вызов, а раз в 16 вызовов прослойка проверяет, не появился ли файл записи `/dev/shm/tfcap`;
- если настоящий драйвер не загрузился, прослойка пишет ошибку и не роняет игру.

Подключение: строки в `zhijack.sh` при наличии `cubegm/tfshim.on` и `TF_DEVICE=GB350` делают `export PICOARCH_DRIVER=/mnt/sdcard/cubegm/tfshim_gb350.so`. На диске ничего не подменяется, настоящий `driver_gb350.so` остаётся на месте.

**Запись.** [`tfrec`](../capture/tfrec.c) создаёт в RAM разделяемый сегмент `/dev/shm/tfcap` (2,3 МБ: 3 слота кадров до 640×480 и кольцо звука на 2,7 с). Прослойка видит его и начинает копировать туда кадры (не чаще заданного fps) и звук, никогда не блокируясь: опоздавший `tfrec` просто пропускает перезаписанные кадры. `tfrec` сжимает кадры без потерь (разница с предыдущим кадром + RLE) и отдаёт поток в stdout. Через удалённое управление поток идёт на ПК, где [`pc/r36rec.py`](../pc/r36rec.py) раскладывает его по меткам времени и отдаёт ffmpeg: H.264 + AAC в MP4.

Подводные камни сборки (Zig 0.17):
- 64-битное деление в коде прослойки тянуло импорт несуществующего символа из compiler-rt, и `dlopen` на консоли упал бы. В прослойке нет 64-битного деления, а проверка запрещает импорт без версии glibc;
- линкер привязал `DT_INIT`/`DT_FINI` к экспортируемым трамплинам `_init`/`_fini`, и они выполнились бы при загрузке. [`capture/postlink.py`](../capture/postlink.py) убирает эти записи.

До консоли прослойка прошла проверки на ПК: набор экспортов совпадает с драйвером, все трамплины прыгают в «свою» функцию, а в эмуляторе MIPS (Unicorn) регистры и стек сохраняются, кадры и звук доходят до сегмента побайтно.

**Замер на консоли** (Moonwalker, Mega Drive, запрос на 20 с):

| | |
|---|---|
| записано | 16,9 с: первые ~3 с ушли на старт `tfrec` и подключение прослойки |
| видео | 320×240 (родное разрешение игры), 30 кадров/с, 398 кадров получено, 3 потеряно |
| звук | 48 кГц стерео, без потерь, синхронно с картинкой |
| поток по USB | ~0,6 МБ/с; MP4 — 0,85 МБ |
| игра | заминок не замечено (проверял владелец консоли) |

В меню FrogUI кадры полного размера 640×480, и `tfrec` с пониженным приоритетом успевает взять лишь часть (8 из 126 при быстром листании). Неподвижное меню новых кадров не выводит, поэтому и записывать там нечего.

## 13. Чего нет и что не проверено

- MTP на порту DC невозможен (нет линий данных).
- Проверено только на одной консоли (GB350) и только с Windows 10. С Linux и macOS (libmtp) обычный MTP должен работать, но удалённое управление реализовано только для Windows (WPD).
- Флешка через OTG при работающей службе не проверялась, проверялась только мышка. Служба оставляет порт в режиме хоста, пока устройство подключено, но совместную работу с `usb_host.sh` TreeFrog стоит проверить отдельно.
- Если ПК засыпает, счётчик кадров останавливается, и служба через ~3 с уходит в IDLE. После пробуждения ПК консоль переподключится в ближайшем окне режима устройства, то есть в пределах 4 с.
- Запись работает только для игр, которые идут через picoarch (libretro-ядра). Самостоятельные программы (pcsx4all, PPSSPP, видеоплеер и т. п.) выводят картинку по-своему и не записываются. Прослойка проверена только на GB350.

## 14. Как повторить замеры

```bat
python pc\r36.py sh "devmem 0x1884400C 16; sleep 0.01; devmem 0x1884400C 16"   & rem счётчик кадров
python pc\r36.py sh "cat /tmp/tfusbd.log"                                        & rem журнал службы
python pc\r36.py sh "chrt -p $(pidof tfmtp)"                                      & rem SCHED_IDLE
python pc\r36.py key probe                                                        & rem период перезаписи кнопок
python pc\r36.py shot screen.png
python pc\r36rec.py game.mp4 --seconds 20 --raw game.tfr                         & rem запись
```
